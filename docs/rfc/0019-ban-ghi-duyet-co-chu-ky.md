## 1. Problem

On a real home (`--target linux`, Profile A) the owner is often not in front of the box. Today an
`ask` can be answered only by `local_grammar` (words typed or spoken on the device) or `ui` (the
box's local page) — `HUMAN_SOURCES` in `python/neuroedge/actions/confirmation.py:36`. Every other
source is refused as `tool_confirm_rejected` ("only a person on the device may answer"). So an
`ask` raised while the owner is away expires, and the user's only working path is to open the
local page from inside the home network (DP-A-05, done).

The obvious shortcut — let the brain's chat (NeuroClaw's Telegram bot) relay "yes" — is exactly the
hole DP-COM-04 closes: the brain is untrusted (threat model §2l). A compromised brain, or a chat
gateway in NeuroEdge Cloud, could fabricate a "yes". Q-76 says it plainly: **approvals do not pass
through the brain.**

## 2. Why the Current Contracts Do Not Solve It

- `tool-call.v1.json` `$defs/source` allows built-ins, `bridge:<id>` and `mcp:<client>`
  (RFC-0017). None of them names a remote person; borrowing `ui` for a chat message would lie in
  every trace.
- RFC-0006 §3 defines the confirmation as single use, bound to a gate digest, with a TTL — but it
  assumes the answer is produced *on the device*, so it has no notion of a message that travels
  over a network and could be replayed, delayed or forged.
- `TODOS.md` #62 (deferred by the product owner, 2026-10-11) already fixes the shape — "approval
  records (id, nonce, expiry, digest)" — but no contract defines them.

## 3. Proposed Change

### 3a. The source `chat:<id>`

`$defs/source` pattern:

```diff
-        { "pattern": "^(bridge|mcp):[a-z][a-z0-9_]{0,31}$" }
+        { "pattern": "^(bridge|mcp):[a-z][a-z0-9_]{0,31}$" },
+        { "pattern": "^chat:[a-z][a-z0-9_]{0,15}:[0-9]{1,20}$" }
```

`chat:<channel>:<user id>`, for example `chat:telegram:123456789`. The runtime assigns it from the
verified record (§3c), never from the message text. It is **not** added to `HUMAN_SOURCES`
statically: `ConfirmationBook` accepts a `chat:` source only through `take_record()` (§3c), so
`take(confirm_id, "chat:telegram:1", …)` from any other path is still refused.

### 3b. The approval record

The box signs a record when it *sends* the question, and accepts the answer only when it carries
that record back unchanged plus the owner's decision. Encoding: compact JWS (RFC 7515), `EdDSA`
(Ed25519), key generated by `neuroedge pair init` as `approval.key` (0600, never leaves the box,
like `issuer.key`). Claims:

| Claim | Meaning |
|:---|:---|
| `cid` | confirmation id (`confirm_N`) |
| `gd` | `gate_digest` of the gate that asked (RFC-0008) |
| `act` | action name and a SHA-256 of its canonical arguments |
| `nonce` | 16 random bytes, base64url; the box keeps spent nonces until `exp` |
| `iat`, `exp` | `exp − iat` = the question's TTL (`max(3 × p95, 10 s)`, RFC-0006), never more than 15 minutes |
| `aud` | the owner's chat identity (`chat:telegram:<id>`) the record was sent to |
| `bot` | the SHA-256 of the box's approval bot token (§3e), so a record sent by any other bot fails |

The bot's buttons carry only a short handle (`<cid>:<nonce prefix>`, Telegram `callback_data` is
64 bytes); the full record stays on the box, keyed by the handle. A press is accepted when:

1. the callback came from the box's own bot session (long polling or webhook of the token in
   §3e), from the user id named in `aud`;
2. the record's signature verifies with `approval.key`;
3. `nonce` is unspent, `exp` not passed, `cid` still `pending`;
4. `gd` equals the gate's current digest, and `act` the pending call (RFC-0006 rules);
5. fewer than the hourly cap of remote approvals has been used (§9 Q2: `[approvals] remote_per_hour`,
   default 10, hard ceiling 30).

Any failure is `tool_confirm_rejected` with a `reason` from a closed list: `bad_signature`,
`nonce_reused`, `expired`, `gate_changed`, `not_owner`, `wrong_bot`, `over_cap`.

### 3c. Confirmation semantics (amends RFC-0006 §3)

```text
HUMAN_SOURCES = ("local_grammar", "ui")          # unchanged: on the device
REMOTE_HUMAN  = "chat:<channel>:<id>"            # only via take_record(record, press)
```

`ConfirmationBook.take_record()` runs §3b checks 1–5, then the same single-use spend as `take()`.
A `chat:` "yes" therefore has every property of a local one (single use, digest bound, TTL, the
4-question cap of DP-COM-09) plus a signature and a nonce. A "no" (`decline`) from a verified
record is accepted the same way; an unverified "no" is still refused (a forged "no" is a denial of
service, but it is traced and does not run anything).

### 3d. Trace

`tool_confirmed` and `tool_confirm_declined` gain an optional `record` object: `{nonce, iat, exp,
aud}` — never the signature or the bot token. `tool_confirm_rejected.reason` takes the values of
§3b. `trace.v1.json` already allows extra keys in `data`; no schema file changes. `replay`
re-checks that every `chat:` confirmation names a record whose `exp` follows the question's
`iat` and that no nonce appears twice.

### 3e. Only the box's own bot (DP-A-06)

`agent.toml` `[approvals.telegram]` names a token file. At start the box refuses (exit 2, NE error)
when that token equals the brain's bot token — read from the NeuroClaw config path given by
`--brain-config`, or recorded by `neuroedge install --profile full` — or when no token is
configured but an `ask` gate allows `chat:` answers. The box never sends a question through the
brain; the brain only learns "not done yet, the owner was asked" (TC-COM-08-1 wording).

### 3f. Relation to verification steps (TSK-I2d-20)

A user-declared verification step (Q-73: code, voice, face, keypad…) would produce a *fact*; an
approval record produces a *confirmation*. They meet only in `on_block`: a gate may require both.
This RFC adds no `on_block` key; TSK-I2d-20 may add `confirms_via: [ui, chat]` later.

## 5. Safety Impact

This RFC **adds a way to confirm**, so it can only make an `ask` easier to pass. Bounds:

- No gate becomes laxer by itself: the gate still blocks, still asks; only who may answer widens,
  and only for an owner who proved presence with a code shown on the box (§9 Q1).
- A compromised brain cannot answer: it holds neither `approval.key` nor the approval bot token,
  and the bot refuses to be the brain's (§3e).
- A stolen phone or chat account can answer, within the cap and only for questions that are
  pending — the residual risk, shown as a risk label `risk=remote_approval` at start and in
  `status` (DP-COM-06), per Q-73.
- Fail closed: no key, no token, an unreadable nonce store ⇒ every `chat:` answer is refused.

## 6. Alternatives Considered and Rejected

| Alternative | Reason for Rejection |
|:---|:---|
| Relay "yes" through the brain's chat | The brain is untrusted (DP-COM-04, Q-76) |
| Add `chat` to `HUMAN_SOURCES` with no record | Any process that can call `take()` with that string answers as the owner |
| Passkey (WebAuthn) page opened from a chat button (Q-76) | Stronger, but needs a public HTTPS origin for the box or the cloud relay; kept as a later method, it fits §3c unchanged |
| HMAC instead of Ed25519 | Same security on one box, but a cloud relay that only forwards could not be given a verify-only key later |

## 9. Decisions on the Open Questions (product owner, 2026-10-16, Q-89)

1. **Pairing the owner: a one-time code shown on the box, sent to the bot.** `neuroedge pair owner`
   (CLI) or the local page shows a code: 8 characters from an unambiguous alphabet, single use,
   valid 10 minutes, one pending code at a time. The owner sends `/pair <code>` to the approval bot
   from a private chat; the box binds that Telegram user id as `aud`. The code is displayed only on
   the home machine (FR-CH-03 unchanged): whoever reads it becomes the owner, so it is never sent
   through the brain, logged, or written to a trace; a wrong code counts against the same limit as a
   bad record, and five wrong codes void the pending code. Pairing replaces any previous owner and
   is traced (`owner_paired`, chat id only).
2. **Cap: configurable, default 10 per hour.** `agent.toml` `[approvals] remote_per_hour`, integer
   1–30; a larger value is refused at load (exit 2). The window is a sliding hour on the monotonic
   clock; once spent, `over_cap` until a local approval (`local_grammar` or `ui`) resets it.
3. **Scope: every `ask`.** No `gate.v1` key is added; a remote answer is bounded by the cap, the
   15-minute TTL and the `risk=remote_approval` label. A gate that must stay local-only waits for
   TSK-I2d-20 (`confirms_via`, §3f).
4. **Revocation: on the box and from the bot.** `neuroedge pair owner --revoke` locally, or `/revoke`
   sent to the approval bot by the paired owner. The bot can only revoke, never grant; pending
   records for that owner are voided at once. A hijacked account that revokes only denies service.
